# PRD: Workspace Project Board MVP

## Goal

Создать desktop-приложение, которое превращает выбранную пользователем папку с проектами в управляемый Workspace с Board и Table views, проектными properties и быстрым доступом к файлам проекта.

MVP должен позволить SMB-команде подключить существующую файловую структуру, увидеть проекты по статусам, управлять свойствами проектов и работать с проектной папкой без переноса данных в отдельную PM-систему.

## Background

Команды часто хранят проекты как папки на локальном диске, сетевом диске или в синхронизируемой директории. Такая структура удобна для файлов, но плохо подходит для обзора статусов, фильтрации, поиска и управления свойствами проектов.

Workspace Project Board должен дать Notion-like слой поверх существующих папок, сохраняя файловую систему как источник проектов. Локальные project metadata, views и properties должны храниться local-first через `any local` / локальный `any-store`, чтобы позже поверх этой модели можно было добавить `any sync`.

## Product Definitions

- Workspace: добавленная пользователем корневая папка проектов вместе с сохранёнными настройками, views, roles и properties.
- Project: папка, определённая как проект по правилам Workspace.
- View: сохранённый способ отображения проектов внутри Workspace, например Board или Table.
- Property: поле проекта, которое отображается в карточках, таблице и правой панели.
- Value: значение property для конкретного проекта или доступный вариант для select-property.
- Folder role: роль папки в дереве Workspace: `group`, `status` или `project`.

## MVP Scope

MVP включает:

- добавление Workspace из выбранной папки;
- сохранение списка Workspaces;
- удаление, переименование и перемещение Workspaces в списке;
- настройку дерева папок Workspace через роли `group`, `status`, `project`;
- поиск проектов внутри активного Workspace;
- Board view с группировкой проектов по статусам;
- Table view со строками проектов и выбранными properties;
- добавление и удаление views внутри Workspace;
- сохранение имени, типа, порядка и настроек properties для каждого view;
- правую панель проекта, открываемую из карточки или строки;
- отображение `Name`, `Status` и кастомных properties в панели проекта;
- отображение файловой структуры проекта в панели проекта;
- открытие файлов и переход в папки из панели проекта;
- базовые properties `Name` и `Status`;
- кастомные properties типов `text`, `number`, `single select`, `multi select`, `date`;
- добавление, удаление, изменение, перемещение и скрытие properties;
- добавление, удаление, изменение, перемещение и скрытие values у select-properties;
- local-first сохранение Workspace data через `any local` / `any-store`.

## Out Of Scope

В MVP не входят:

- авторизация;
- роли пользователей и права доступа;
- multi-user collaboration;
- пользовательская функция синхронизации через `any sync`;
- облачный backend как обязательная часть продукта;
- мобильное приложение;
- публичный web-доступ к Workspace;
- встроенный редактор файлов;
- полноценный таск-трекер с задачами, комментариями и исполнителями;
- интеграции с внешними PM-системами;
- импорт данных из Notion, Trello, Jira или других инструментов;
- автоматическая классификация проектов без настройки пользователем.

## User Stories

- Как пользователь, я хочу добавить папку как Workspace, чтобы увидеть существующие проекты в приложении.
- Как пользователь, я хочу назначать папкам роли `group`, `status` и `project`, чтобы приложение правильно понимало мою структуру проектов.
- Как пользователь, я хочу видеть проекты на Board view по статусам, чтобы быстро понимать состояние работ.
- Как пользователь, я хочу видеть проекты в Table view, чтобы сравнивать свойства проектов в списке.
- Как пользователь, я хочу добавлять и удалять views, чтобы иметь разные способы просмотра одного Workspace.
- Как пользователь, я хочу выбирать, какие properties видны в конкретном view, чтобы не перегружать рабочую область.
- Как пользователь, я хочу создавать кастомные properties, чтобы хранить важные для команды данные рядом с проектами.
- Как пользователь, я хочу редактировать property values у проекта, чтобы поддерживать актуальную информацию без отдельной таблицы.
- Как пользователь, я хочу открыть проектную карточку в правой панели, чтобы увидеть свойства и файлы проекта без ухода с основного экрана.
- Как пользователь, я хочу открывать файлы и папки проекта из приложения, чтобы быстро перейти к рабочим материалам.
- Как пользователь, я хочу искать проекты, чтобы находить нужную папку среди большого количества проектов.
- Как пользователь, я хочу, чтобы мои Workspaces, views и properties сохранялись локально, чтобы не настраивать их заново после перезапуска приложения.

## Functional Requirements

### Workspace Management

- Пользователь может добавить новый Workspace, выбрав корневую папку.
- Приложение сохраняет Workspace после добавления.
- Пользователь может переименовать Workspace.
- Пользователь может удалить Workspace из приложения без удаления файлов на диске.
- Пользователь может изменить порядок Workspaces в Left Panel.
- Приложение открывает последний активный Workspace после перезапуска, если он всё ещё доступен.

### Folder Role Configuration

- Settings активного Workspace показывает дерево папок внутри выбранной корневой папки.
- Пользователь может назначить папке роль `group`, `status` или `project`.
- Папка с ролью `group` используется как контейнер; приложение ищет проекты внутри неё.
- Папка с ролью `status` задаёт статус проектам внутри неё и используется как колонка Board.
- Папка с ролью `project` считается проектом; приложение не ищет проекты глубже внутри этой папки.
- Изменение роли папки обновляет список проектов и их статусы в Board и Table.
- Приложение сохраняет роли папок локально для каждого Workspace.

### Project Discovery

- Приложение строит список проектов из дерева Workspace с учётом folder roles.
- Project `Name` по умолчанию соответствует имени проектной папки.
- Project `Status` в MVP определяется статусной папкой, в которой найден проект.
- Один и тот же проект не должен отображаться дублирующими карточками или строками.
- Проекты за пределами корневой папки Workspace не отображаются.

### Views

- Workspace содержит один или несколько views.
- Пользователь может добавить Board view.
- Пользователь может добавить Table view.
- Пользователь может удалить view, если после удаления в Workspace остаётся хотя бы один view.
- Пользователь может переименовать view.
- Пользователь может изменить порядок views.
- Workspace сохраняет тип, имя, порядок и настройки каждого view.
- Настройки view включают отображаемые properties, порядок properties и скрытые properties.
- Удаление view не удаляет проекты, properties или values.

### Board View

- Board view отображает проекты как карточки.
- Board view группирует карточки по `Status`.
- Каждая status-группа отображает название статуса.
- Карточка проекта отображает `Name`, `Status` и выбранные для view properties.
- Клик по карточке открывает правую панель проекта.
- Board view обновляется после изменения folder roles, project properties или view settings.

### Table View

- Table view отображает проекты строками.
- Каждая строка отображает `Name`, `Status` и выбранные для view properties.
- Пользователь может скрывать и показывать columns через настройки properties view.
- Клик по строке проекта открывает правую панель проекта.
- Table view обновляется после изменения folder roles, project properties или view settings.

### Project Detail Panel

- Правая панель открывается при выборе проекта в Board или Table.
- Панель показывает `Name`, `Status` и кастомные properties проекта.
- Пользователь может редактировать values кастомных properties из панели.
- Панель показывает файловую структуру выбранного проекта.
- Пользователь может открыть файл из панели проекта.
- Пользователь может перейти в папку из панели проекта.
- Панель закрывается без потери несохранённых изменений, если изменение property уже было применено.

### Properties

- Системные properties `Name` и `Status` доступны для каждого проекта.
- Пользователь может создать кастомную property типа `text`.
- Пользователь может создать кастомную property типа `number`.
- Пользователь может создать кастомную property типа `single select`.
- Пользователь может создать кастомную property типа `multi select`.
- Пользователь может создать кастомную property типа `date`.
- Пользователь может переименовать кастомную property.
- Пользователь может удалить кастомную property.
- Пользователь может изменить порядок properties.
- Пользователь может скрыть property в конкретном view без удаления самой property.
- Удаление property удаляет её values из product data после подтверждения пользователем.

### Select Values

- Для `single select` и `multi select` пользователь может создавать values.
- Пользователь может переименовать select value.
- Пользователь может удалить select value.
- Пользователь может изменить порядок select values.
- Пользователь может скрыть select value, если это поддерживается настройками отображения.
- `single select` допускает не больше одного выбранного value для проекта.
- `multi select` допускает несколько выбранных values для проекта.

### Search

- Search ищет проекты внутри активного Workspace.
- Search должен учитывать project `Name`.
- Search должен учитывать видимые text-like property values, если они есть.
- Результат поиска должен открывать найденный проект в текущем view или через правую панель.
- Пустой поисковый запрос возвращает обычное отображение активного view.

### Local Persistence

- Приложение сохраняет Workspaces, folder roles, views, properties и values локально.
- Данные сохраняются через `any local` / локальный `any-store`.
- Перезапуск приложения не должен сбрасывать Workspaces, views, roles, properties или values.
- Локальная модель хранения должна быть пригодна для будущего `any sync`.
- UI state, который не является product data, не должен смешиваться с Workspace product data.

### File-System Safety

- Приложение должно работать только внутри выбранной корневой папки Workspace при обходе дерева проекта.
- Удаление Workspace из приложения не должно удалять папку или файлы на диске.
- Открытие файла или папки должно использовать безопасный путь внутри Workspace.
- Если папка Workspace недоступна, приложение должно показать понятное состояние ошибки.
- Если проектная папка была удалена или переименована вне приложения, приложение должно обновить отображение без падения.

## Edge Cases

- Корневая папка Workspace пуста.
- Корневая папка Workspace недоступна после перезапуска приложения.
- Пользователь удалил или переименовал папку проекта вне приложения.
- В дереве нет папок со статусной ролью.
- В статусной папке нет проектов.
- Одна папка ранее имела role `project`, но пользователь меняет её на `group` или `status`.
- Пользователь пытается удалить последний view в Workspace.
- Пользователь удаляет property, которая уже имеет values у проектов.
- Пользователь удаляет select value, который выбран в одном или нескольких проектах.
- Project name совпадает у нескольких папок в разных статусах.
- Путь содержит пробелы, Unicode-символы или символы, требующие экранирования.
- Поиск не находит проектов.
- Большой Workspace содержит много папок и файлов.

## Acceptance Criteria

- Пользователь может добавить Workspace из локальной папки и увидеть его в Left Panel.
- После настройки folder roles приложение отображает найденные проекты в Board view.
- Board view группирует проекты по статусам из папок с ролью `status`.
- Table view отображает те же проекты строками.
- Переключение между Board и Table не меняет project data.
- Пользователь может добавить новый view внутри Workspace.
- Пользователь может удалить view, если это не последний view Workspace.
- Workspace сохраняет views и настройки отображаемых properties после перезапуска приложения.
- Пользователь может создать custom property каждого MVP-типа: `text`, `number`, `single select`, `multi select`, `date`.
- Пользователь может скрыть property в одном view, и это не удаляет property из Workspace.
- Пользователь может открыть проект из Board или Table в правой панели.
- Правая панель показывает project properties и файловую структуру проекта.
- Пользователь может открыть файл или папку проекта из правой панели.
- Search находит проект по имени.
- Удаление Workspace из приложения не удаляет файлы на диске.
- Приложение не показывает проекты за пределами выбранной корневой папки Workspace.
- Workspaces, roles, views, properties и values сохраняются локально через `any local` / `any-store`.

## Dependencies And Constraints

- Продукт работает с локальной файловой системой как источником проектов.
- Product data хранится local-first через `any local` / локальный `any-store`.
- Будущий `any sync` должен накладываться поверх local-first модели, а не заменять её.
- MVP не требует авторизации и облачного backend.
- Любые изменения, которые затрагивают публичные contracts, data model или storage model, должны быть отражены в `docs/data-model.md`, API contracts и ADR на следующих этапах spec-first процесса.

## Risks

- Сложные или неоднородные структуры папок могут сделать автоматическое обнаружение проектов неоднозначным.
- Если product data привязать к нестабильному абсолютному пути, переименование или перемещение папок может привести к потере связи с properties.
- Большие деревья папок могут потребовать оптимизации сканирования и lazy loading.
- Удаление properties или select values может неожиданно удалить важные project metadata, если не будет подтверждения и понятного UX.
- Будущий sync-слой может быть сложнее добавить, если local data model будет смешана с UI-only state.

## Open Questions

- Как именно идентифицировать проект: абсолютным путём, относительным путём внутри Workspace или стабильным локальным id?
- Какой статус назначать проекту, если он найден вне папки с ролью `status`?
- Нужно ли разрешать вложенные status-группы или только один уровень status folders?
- Должен ли MVP поддерживать drag and drop проектов между статусами как физическое перемещение папок?
- Какие property values должны участвовать в поиске кроме project `Name`?
- Нужна ли история изменений properties в local-first модели?
