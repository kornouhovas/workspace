# Explicit project Status moves in Electron

Preview/expanded Project Detail, Board cards and Table Status cells can select an existing derived Status. Board card drops and Table handle drops use the same operation. This is an explicit filesystem operation behind WorkspaceServiceClient → renderer transport → sandboxed preload IPC → main dispatcher/backend. System Status remains derived; custom property writes remain unavailable. Drag destinations use only verified stable Status IDs. Electron uses the existing JSON settings/views/properties adapters. This operation does not wire the Go sidecar or implement ADR-004's proposed general identity registry.

`workspace.getProjectStatusOptions({ workspaceId, projectId })` returns `{ projectId, options }`. Each option includes the stable derived `id`, localized display inputs (`name`, `source`, `color`), verified folder `relativePath`, `current`, backend display locators `from`/`to`, and nullable `disabledReason`. Empty status folders are included. Duplicate names or slugs have distinct path-based IDs; existing name-based colors/filters remain compatible through `legacyId`. No status has no unambiguous destination in this runtime, so a change to it is disabled with an explanation. Nested status destinations are disabled.

`workspace.moveProjectStatus({ workspaceId, projectId, statusValueId })` resolves the explicit Workspace source and current project, accepts a derived stable Status ID, and preserves the source folder basename. Caller paths/names are not destinations. Current Status returns `{ state: "unchanged", projectId, from, to }`; successful moves return `{ state: "completed", projectId, from, to, statusValueId }`. Repeated requests for the same project while pending reject with `PROJECT_MOVE_PENDING`. Settings mutations and discovery publications share a barrier while the move runs.

The backend rejects unavailable sources/projects/statuses, traversal, symlink source/target ancestors, nesting/overlapping targets and existing targets. It exclusively creates the final target and every copied child (`mkdir`, exclusive file creation, symlink creation without following links). An existing empty or nonempty target is never replaced or merged, including a target created between preflight and reservation. Hidden entries, empty folders, regular file modes/times, and symlink contents are copied. Special entries such as sockets are rejected. Copying requires temporary disk space for another complete project copy and takes time proportional to its contents; no percentage estimate or production delay is added.

## Journal, consistency and recovery

A single `projectMove` journal is written atomically to settings before any filesystem mutation. It records source/project IDs, old/new relative locators, the unique holding path, source and target device/inode evidence, ownership marker, content manifest and phase:

1. `prepared` → exclusively reserve target and mark ownership.
2. `copying` → copy all entries and verify bytes/tree/modes against the source.
3. `copied` → exclusively create a hidden holding container on the original filesystem, durably record its device/inode ownership, then move the source inside it.
4. `held` → verify the authoritative holding contents again, including external edits after the initial copy. Atomically commit remapped roles, existing opaque ID's locator, and `committed` journal together.
5. `committed` → verify both copies, remove the verified holding copy/empty container and ownership marker, then clear the journal.

`projectLocators[sourceId][existingProjectId] = { path, dev, ino }` retains only explicit move identities. Every scan validates that target evidence. New occupants of an old locator receive a different ID; replacement targets never inherit moved values/history. A verified rollback refreshes an existing alias's inode. This does not recognize arbitrary external moves or redesign unmoved legacy identities. All role snapshots for that root, including shared Workspace bindings and retained `rulesByRoot`, move with the project subtree. Property documents/history IDs and saved view settings are not rewritten.

Recovery runs before scan, project lookup and view projection publish. Before commit, the original/holding copy is authoritative and restoration exclusively creates the old path. After commit, the target is authoritative and cleanup resumes only after verification. Unknown contents, changed inode, occupied original/holding location, unavailable paths or failed restoration retain all available copies and the journal and report `MOVE_RECOVERY_REQUIRED`; recovery never deletes an unknown target. A journal or verified holding copy must not be removed manually to silence this error. Resolve the conflicting location or filesystem availability, retain the authoritative copy, and retry/restart. Tests use isolated fixtures and controlled backend hooks for each phase.

A copy failure can leave an incomplete target whose staged directory modes differ from the manifest (for example a restrictive source directory before its final chmod). That ambiguity retains the target and journal and blocks discovery with a recovery error. It is not published as another project. A verified unchanged partial target is removed before recovery clears the journal.

An interruption or marker-write failure after exclusive target creation, before target identity is recorded, leaves a `prepared` journal with ambiguous ownership. Recovery retains that target and journal and blocks discovery. Only a witnessed `mkdir` `EEXIST` result proves that this operation never reserved the target; that branch clears its own prepared intent and leaves the foreign target untouched.

Holding-container cleanup also requires recorded device/inode ownership. A foreign existing container, a replacement, or an interruption between its creation and ownership recording retains the container and journal and blocks recovery before any copies are changed. Recovery never removes an unowned empty container.

A cleanup failure after committed metadata that cannot be recovered returns `{ state: "recovery-required", committed: true, projectId, from, to, project, error }`. It is an explicit error result; the renderer updates the open project's locator and clears pending. It must not report success or keep showing the old file tree. A transient postcommit failure followed by verified successful cleanup returns `completed` with the new location. Before commit errors reject; a successful rollback restores the old location and identity.

This is a verified copy protocol, not an atomic filesystem snapshot. An external process holding a writable file descriptor can write after the last verification; the app cannot lock unrelated writers through portable Node APIs. Writers should finish before moving a project. Detected edits before publication abort and preserve the authoritative source; ambiguous edits retain recovery data. Atomic settings writes protect process interruption; power loss guarantees of the underlying filesystem are not extended by this operation.

## Renderer operation state

The compact animated indicator sits immediately after Sidebar in the left header navigation group and remains reachable with the sidebar hidden. It exists only during the backend promise, opens keyboard-accessible details (project, from, to, state), has an accessible live status and respects reduced motion. Status controls reject repeated pending actions. Success/error removes the indicator; errors use visible notifications and recovery details. Tests inject latency/faults through backend test options only, never renderer payloads or production delays.

## Board and Table Status actions (workspace-d9h)

Visible Status in a Board card or Table cell opens the shared keyboard accessible picker. Selecting a different available Status invokes `getProjectStatusOptions` / `moveProjectStatus`; ordinary project opening and custom property editors keep their actions. Hiding Status does not change visibility settings: the Table handle opens the same picker on click or keyboard activation.

Board drag starts from card name/background and highlights available Status columns, including empty columns. Table drag starts only from its compact internal left handle, visible on row hover or focus. During drag, Table shows every fresh backend Status option as an explicit zone in flat, Status, other-property and Multi-select groupings, including empty and filtered statuses. A target is a zone's stable Status ID, never a row or custom value. Multiple occurrences retain one project ID. Shared horizontal/vertical scrolling remains available during drag.

Escape, cancellation, outside drop and current Status make no move. Unavailable No status and nested targets explain their reason. Pending blocks repeat actions and uses the common header indicator; failures are visible. Success refreshes projections, counts, tabs and file trees with the original project ID. A moved row may disappear under existing filters. No custom values/history, view grouping/filter settings, manual group order or visibility settings are written by these actions. Folder safety, no-clobber and journal/recovery are defined by the existing Status move API.
