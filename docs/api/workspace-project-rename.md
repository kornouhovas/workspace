# Project folder rename in Electron

`workspace.renameProject({ workspaceId, projectId, name })` renames the real project folder in its existing parent. Name is a single visible folder component, with no separators, controls or surrounding whitespace; Windows also rejects reserved names, ADS syntax and normalized trailing dots. The dispatcher resolves the opaque ID against the explicit Workspace's current source. Renderer-supplied destination paths are never accepted. Status, contents, property values/history, saved view ordering and session identities remain attached to the same project.

Calls follow WorkspaceServiceClient → sandboxed preload IPC → dispatcher → backend → bundled short-lived native directory helper. Active settings/views/properties storage remains JSON. This does not connect Go persistence or implement ADR-004's proposed general identity registry.

The compact Rename project action is in preview and expanded Project Detail. Its dialog starts with the current name, keeps failed drafts and associated errors, prevents duplicate submission and composing Enter, and restores trigger focus on Cancel/Escape/close. Pending disables confirmation and cancellation until the backend settles. A keyboard reachable details button inside the dialog exposes the old/new display locators while its modal focus trap keeps the header unavailable. Confirming the same name closes without a filesystem request. A confirmed rename refreshes Board/Table projection, open project tabs, preview and file tree, including opened tabs in Workspaces sharing its source.

## Results and errors

An unchanged name returns `{ state: "unchanged", projectId, from, to }`. Success returns `{ state: "completed", projectId, from, to }`, optionally `recovered: true` after verified recovery. No success is reported merely because metadata or physical work has started. A verified physical completion whose metadata/cleanup cannot recover returns `{ state: "recovery-required", physicalCompleted: true, committed, projectId, from, to, project, error }`. The UI immediately adopts the verified new name/locator, clears the old file tree, retains an error and does not announce success. Native IPC registration serializes rename failures as `{ state: "failed", error: { code, message } }`; WorkspaceServiceClient restores an Error with the service code for localized UI feedback. Direct domain/dispatcher calls reject on failure.

Invalid names use `INVALID_PROJECT_NAME`; an existing file/folder is `PROJECT_NAME_CONFLICT`; a repeated rename or simultaneous Status move is `PROJECT_MOVE_PENDING`. An unavailable OS mechanism is `PROJECT_RENAME_GUARD_UNAVAILABLE`. Ambiguous ownership, replacement, unavailable parents or failed recovery use `RENAME_RECOVERY_REQUIRED`, retain available folders and journal, and block discovery publication. Do not manually remove a staging folder or journal to silence this error. Resolve source availability/conflicts, retain authoritative contents and retry/restart.

## Filesystem protocol and identity

An atomic `projectRename` settings journal records version, UUID, source/project IDs, root, original/new/staging relative paths, parent device/inode, project device/inode and phase. The source and parent must be real directories; every source-relative component is opened without following symlinks/reparse points. The native operation verifies parent and project identity and never replaces an existing destination, including an empty directory created after preflight.

1. `prepared`: write intent before a filesystem mutation.
2. Exclusively rename original to a unique hidden `.workspace-rename-<UUID>` sibling; record `staged`.
3. Write `finalizing`, then exclusively rename the staging folder to the new name. This two-step sequence also supports case-only changes on an insensitive filesystem without copying or replacing contents.
4. Verify the final identity. Atomically remap roles for every shared-source binding/retained root, update `projectLocators[sourceId][existingId]`, and write `committed`.
5. Clear the journal. Folder inode and contents are preserved; values/history and saved view documents are not rewritten. A later occupant of the original path gets a distinct identity without inherited metadata.

Recovery runs under the same mutation/read barrier as Status moves before source discovery. Before the final rename, the owned staging folder is restored exclusively to the original location; an untouched original clears prepared intent. After the observed final rename, verified final ownership commits metadata forward. A process interruption between syscall completion and journal update is resolved by exact directory spelling plus device/inode evidence. Exact spelling is necessary for case-only rename. Unknown, multiply occupied or changed locations remain untouched with a visible recovery error. Parent substitution is never repaired by writing to the replacement parent.

This preserves process-interruption consistency, not a guarantee beyond underlying filesystem power-loss durability. Portable directory APIs cannot atomically compare an expected source inode and rename against arbitrary external replacement; ownership is checked before the native syscall and again after it in the native helper and backend. Native subprocess tests deliberately substitute a directory/symlink after the first identity check; the no-follow exclusive syscall may relocate the substituted entry inside the selected source, but the postcheck rejects success and retains all unknown entries. Backend recovery tests verify blocked publication and unchanged identity/property metadata. A detected mismatch retains ambiguous entries/journal and blocks publication instead of assigning old metadata or deleting unknown contents.

## OS enforcement and validation status

The helper's macOS implementation reuses the mandatory per-process sandbox from [ADR-009](../adr/009-project-creation-os-guard.md), anchored to the selected real source. Pinned `O_NOFOLLOW` parent handles plus `renameatx_np(RENAME_EXCL)` preserve directory identity/no-clobber; sandbox mediation denies writes when an unsandboxed external process moves the held parent or entire source outside the lexical source. No system settings or profile installation are changed. Missing/refused sandbox or non-cgo Darwin build fails before mutation. Native macOS subprocess regression tests cover moved parent/root, substituted project, symlink and target conflict.

The Windows implementation extends ADR-009's existing local fixed NTFS ancestry reservations. It holds every ancestor without share-write/share-delete, rejects reparse components with `OBJ_DONT_REPARSE` and `FILE_OPEN_REPARSE_POINT`, reserves the source with DELETE access and performs handle-relative `FileRenameInformation` with Replace=false. Native identity is checked before mutation. The same local-volume/ancestry access restrictions as creation apply. Windows cross-compilation establishes buildability; native adversarial validation is still required.

Linux safe implementation is required by the current task and is incomplete. The development build currently refuses rename before mutation when no enforceable helper exists; this is not an accepted Linux support exception or completed implementation. Landlock/inode rules and pinned root/mount handles alone do not enforce the required lexical boundary against an unsandboxed external source rename. An AppArmor candidate requires proof of mediation/rename ordering and safe policy lifetime; administrative deployment permission alone does not prove the guarantee. No policy has been installed. See the task evidence for outstanding platform decisions and native stand requirements.
