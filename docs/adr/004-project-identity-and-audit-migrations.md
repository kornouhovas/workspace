# ADR-004: Stable Project Registry And Conservative Audit Migrations

## Status

Proposed — требуется явное принятие человеком перед реализацией A1.

Date: 2026-09-18

Запрос «написать план» разрешает подготовить этот документ, но не меняет стратегию идентичности работающего приложения. Ограничение: `AGENTS.md`, раздел Forbidden Without Explicit Approval, «change project identity strategy».

## Context

Аудит A1 показал: `createFolderObjectId(sourceFolderId, relativePath)` заново вычисляет ID при rename. Данные остаются в store под старым ключом и исчезают из проекции. UUID без механизма сопоставления папок тоже не решает задачу.

Electron сейчас использует JSON transitional stores; ADR-001 оставляет any-store целевым durable store, ADR-002 откладывает packaged sidecar lifecycle. Эта работа не переводит приложение на другую технологию хранения и не запускает sidecar автоматически.

## Alternatives

1. **Реестр и filesystem evidence — рекомендуется.** UUID выдаётся однажды, локальные признаки ФС помогают узнавать ту же папку после rename. Нет записи в пользовательские проекты; нужна консервативная обработка неоднозначности и проверка платформ.
2. **ID-маркер внутри каждого проекта.** Переживает некоторые перемещения, но изменяет пользовательские папки и создаёт дубли после копирования. Не выбран.
3. **Только путь или эвристика имени/содержимого.** Проще, но путь нестабилен, а похожее содержимое не доказывает идентичность. Не выбран.

## Proposed Decision

### Identity

- Backend registry хранит `id`, `sourceFolderId`, `currentRelativePath`, `name`, `discoveryState`, timestamps, `filesystemEvidence` и версию схемы.
- Новые проекты получают `project:<uuid>` через существующий injected idFactory/randomUUID.
- Существующий legacy ID сохраняется без изменения как opaque primary key при первой регистрации найденного проекта. Это сохраняет current values и append-only history без массового переписывания ссылок.
- Последующие rename не пересчитывают legacy ID: обновляется только locator.
- `sourceFolderId` и стратегия идентичности самого источника этим ADR не меняются.
- `filesystemEvidence` хранится только локально и не используется как sync identity. Реестр документный; адаптер transitional JSON находится рядом с backend, будущий any-store adapter должен сохранять те же ID.

### Recognition Policy

- Сначала завершить валидированный scan доступного источника, не выходя за root и не следуя symlink наружу.
- В локальном runtime получать serializable evidence из `stat` с bigint: device, inode/file index и время создания, когда оно действительно доступно. Не использовать mtime/ctime как стабильный признак: содержимое и rename могут их менять.
- Автоматически сопоставлять изменившийся путь только при единственном старом и единственном новом наблюдении с проверенным одинаковым evidence в пределах источника/тома. Старый locator должен отсутствовать в завершённом scan.
- Тот же путь с изменившимся доступным evidence означает заменённую папку, а не прежний проект. Новая папка не наследует чужие свойства.
- Отсутствующий или неоднозначный evidence не разрешает автоматический перенос metadata. Старый проект остаётся `missing`, его значения и история сохраняются; новый получает новый ID. При непрерывно существующем пути без надёжного evidence допустима текущая path continuity, но rename на такой ФС не объявляется поддержанным.
- Пустой/частичный scan из-за ошибки доступа не делает все проекты missing. Обновление реестра публикуется только после полного успешного scan.
- Не переносить metadata между source folders/томами по одному имени, размеру или хэшу содержимого. Ручное связывание и copy-across-volume — отдельная будущая задача.

### Support And Limits

До принятия реализации проверить реальный rename на локальной macOS ФС и fixture-тестами адаптер без evidence. Для Windows требуется отдельный runtime smoke на целевой ФС перед заявлением поддержки rename на Windows; mocked stat не заменяет эту проверку. Отсутствующая проверка платформы фиксируется в handoff как ограничение поддержки.

Миграция не может узнать старую папку, если она была переименована до первого сбора evidence. Не прикреплять автоматически осиротевшие legacy values к похожему новому пути.

### Storage And Migration

- Реестр — новое семейство metadata, proposed transitional `projects.json` рядом с текущими settings/views/properties. Путь передаётся явно в тестах и выводится из configPath в runtime. Это ограниченное расширение уже используемого adapter, не замена any-store.
- Для каждого изменяемого файла создать неизменяемую backup перед первой миграцией; записать новую схему через уникальный temp + atomic rename. Ошибка backup/parse/write отменяет публикацию нового состояния.
- Schema markers хранятся в соответствующих data files; read/write не должны терять дополнительные поля новой схемы. Повторная миграция идемпотентна. Неизвестная будущая schemaVersion вызывает ошибку, не downgrade.
- A2 сохраняет существующие legacy view IDs и меняет только выдачу ID новым default views; A7 меняет внутренние storage keys, сохраняя публичные property IDs.
- A3 добавляет сохранённые наборы ролей по источнику без изменения семантики ролей или их текущей области применения между Workspaces.
- A4 сохраняет mapping legacy status ID → новые IDs для обновления filters/colors. При коллизии старого slug невозможно восстановить потерянное различие: прежний объединённый фильтр разворачивается во все соответствующие новые статусы, общий цвет копируется. Это сохраняет фактически видимый набор проектов до исправления.
- A5 использует persisted pending operation в property store и recovery перед обслуживанием затронутых запросов: два JSON-файла не объявляются транзакционными. Повтор recovery не дублирует history.

### Contracts

- React продолжает использовать WorkspaceServiceClient; никаких Node imports или storage calls в renderer.
- Публичные имена service methods остаются прежними; ID из response трактуются как opaque.
- Новые registry/evidence/migration методы — backend-only interfaces, не sidecar routes и не новый preload API.
- При принятии ADR обновить `docs/architecture.md` и `docs/data-model.md` в implementation slice A1, сохранив различие между текущим transitional runtime и целевым any-store.

## Consequences

Преимущества: зарегистрированные проекты переживают подтверждённый rename; текущие значения и история не требуют перепривязки; filesystem evidence не становится primary ID; файлы проектов не изменяются.

Цена: появляется backend registry с миграцией и платформенными ограничениями. Нельзя обещать автоматическое восстановление после любого перемещения. Backup и recovery обязательны для сохранности существующей metadata.
