# ADR 0009: Separate durable folder evidence from current-mount checks

[Issue #70](https://github.com/kornouhovas/workspace/issues/70) requests a decision before storage changes. Propose volume-scoped persistent folder evidence for continuity across runs, with separate fresh mount observations for every filesystem authorization. Legacy associations require explicit reviewed binding; neither a familiar path nor matching inode/birth time establishes their historical volume. **Owner acceptance is pending.** This document changes no runtime behavior and does not authorize live-data repair. It refines [ADR 0004](0004-local-folder-identity-without-markers.md); [ADR 0006](0006-recoverable-project-creation.md) and [ADR 0007](0007-no-replace-project-renames.md) keep their safety guarantees and documented race limits.

## Context and alternatives

At baseline `24400d16`, `src/service/discovery.ts` stores/compares decimal `dev`, `ino`, and `birthtimeNs`. Discovery, background reconciliation, filesystem commands, native Reveal and journals consume that evidence. The #70 disposable-service reproduction changes only stored `dev` and produces `root_identity_conflict`. Matching inode/birth time on inspected folders and a changed device number are consistent with device renumbering; the historical event is unproven because no volume UUID was recorded.

Keeping `dev` as a cross-run identifier rejects valid remounts. Dropping `dev` without a volume boundary can adopt unrelated folders. Paths, timestamps, volume labels, drive letters and content resemblance are not identity. Permanent marker files violate the accepted folder contract. Choose the bounded local evidence policy below, retaining explicit uncertainty and recovery instead of claiming portable or cryptographic identity.

## Evidence and platform contract

Logical source/project/category UUIDs remain independent of filesystem evidence and locators. Evidence is versioned and tagged with platform/provider and machine-local scope. Serialize integers losslessly and validate exact shape; unknown versions/providers never fall back to legacy equality. Store durable evidence separately from the last observed mount and from review authorization.

Machine-local scope uses a backend-owned random installation anchor in machine-local application data, outside the SQLite database and every exported/automatic/pre-migration backup payload. Store its identifier with enrolled evidence; compare it to the current local anchor before accepting continuity. Create it exclusively and atomically on first use, retain it across normal updates, and never overwrite it from a restored database. Same-installation restore can retain scope only while that local anchor survives; copying a database/export to another installation, missing/corrupt anchor, reinstall without it or an unknown anchor requires explicit reviewed enrollment and invalidates reviews/permits. Generate a new anchor on loss instead of reconstructing it from the database. Backup manifests must explain that this local authority is intentionally not restored. The anchor is an installation boundary, not a hardware fingerprint or secret proof of machine identity: copying the whole application-data directory including the anchor is outside automatic transplant detection, just as indistinguishable volume cloning is. Keep that limitation explicit; no anchor is written into a project/source folder.

| Evidence | macOS candidate | Windows candidate | Authority |
| --- | --- | --- | --- |
| Durable volume scope | Filesystem volume UUID from `ATTR_VOL_UUID` | OS volume GUID path, together with the volume serial returned by the opened folder's `FILE_ID_INFO` | Compare only within the enrolled machine/provider scope; not a label, `st_dev`, drive letter or disk partition UUID |
| Durable folder evidence | Persistent file ID (`ATTR_CMN_FILEID`) and positive creation/birth time | Full 128-bit `FILE_ID_INFO.FileId` and positive creation time from the same opened directory | Require supported persistent IDs, volume binding, real directory kind, and no conflicting historical ownership; time is supplementary reuse detection |
| Current-mount observation | Fresh `dev`, native folder evidence and canonical path/ancestor observations | Fresh handle volume/file information, reparse/kind checks, canonical containment and adapter mount observations | Bind a single scan/review/effect; reacquire after restart/remount; never persist as cross-run proof |

The platform columns are a proposed implementation contract, not a tested schema or a claim that every filesystem supplies these attributes. On macOS query returned/valid attributes and persistent-object capability; resolve the actual containing volume, including a source below the mount root. The volume query and directory observation must refer to the same stable mount before and after collection. On Windows collect file information through a directory handle with reparse-point checks, preserve all 128 file-ID bits, resolve the containing volume, and bind its GUID/serial to that handle's volume. A volume can have multiple GUID paths: an unrecognized alias requires review, not inferred equivalence. Never obtain evidence by shell-parsing localized disk labels or letting renderer input choose a native provider.

The private backend adapter returns either sufficient typed evidence or a finite reason: unsupported filesystem/provider, missing attributes, permission denied, disconnected, or changed during observation. Zero, partial, malformed, mixed-volume or contradictory results are insufficient. New native code must have fixed loading/resource provenance, Node and Electron build/package checks and supported-host tests under the existing native boundary; failure to load cannot select a weaker provider. Network shares, virtual providers and removable formats without demonstrated persistence are insufficient until separately validated. Do not synthesize a UUID from a path, `dev`, serial number alone or a folder ID.

UUIDs and file IDs are local evidence, not a guarantee against cloned disks, restored ID reuse or an adversarial filesystem. Detect duplicate volume/folder evidence and competing associations where observable; leave ambiguous matches unresolved. An indistinguishable offline clone cannot be reliably detected without a different identity design. Cross-machine database restore is not automatic reauthorization, even when UUIDs match. No permanent identity markers are introduced.

## Continuity and current authorization

Automatic continuity requires previously enrolled sufficient durable volume AND folder evidence, unchanged within the same machine/provider scope, unique ownership, and a complete fresh contained scan. A changed device number between runs alone then does not retire associations, change logical IDs or lose metadata. Preserve the existing rule that missing/unresolved/mode-inactive records do not silently reactivate; durable equality does not override their required recovery.

Within one scan, preview or command, mount/ancestor/kind/identity changes invalidate the observation even if durable evidence matches. A remount after Preview requires a fresh Preview and explicit Apply. Never make `sameIdentity` globally ignore `dev`: separate durable continuity comparison, current-observation equality and authorization with explicit callers. Refresh and watch hints are observations, not consent. Previously enrolled root evidence cannot authorize an unverified category/project, and vice versa.

Containment, exact authored names, symlink/junction/reparse rejection, alias conflicts, exclusion/archive policy, parent ownership and no-overwrite checks remain mandatory. A child mount with a different volume is blocked for association/mutation in this rollout; do not inherit the source volume onto descendants. Preserve no-replace rename and all repeated pre/post-effect checks. No new filesystem lock, atomic SQLite/filesystem transaction, rollback or power-loss guarantee is claimed.

## Legacy migration and reviewed binding

#71 adds an additive versioned migration after the actual current migration tip, with a verified pre-migration backup. Preserve old identity JSON, logical IDs, exact values, source configuration, exclusions, category links/labels, independent revisions, sessions, views and journal bytes/history. Do not edit old migration files or translate old `dev` into a volume UUID. A nullable new evidence field or equivalent record marks every existing source/project/category as legacy-unverified, even if its old triple still matches. Fresh records enroll only from sufficient new evidence. Read/list/metadata editing remains available without implying folder access.

Recovery is a reviewed metadata operation, never a folder move or merge:

1. Show the saved source and retained projects/categories, reason and available actions in Sources and affected project contexts. Explain that the old volume was not recorded and continuity cannot be proven. Connect the expected disk and Refresh, Cancel, or select **Review folder association**. Selecting a folder only begins inspection.
2. Preview one existing source root at its saved canonical location and an explicit mapping of selected legacy category/project IDs to fresh eligible folders. Source relocation/merging remains separate scope. Show every proposed mapping, old/new paths, grouped parents, retained/unmapped records, properties preserved, and journal blockers. No select-all inferred consent. The user explicitly confirms that selected folders should own the retained data; this is new authorization, not proof they are historically identical. Root-only approval never bulk-binds descendants.
3. Same-path/inode/birth-time similarity may suggest a candidate, but cannot select or Apply it automatically. A mapping must be one-to-one, source-contained, within the current discovery mode, not linked, reserved, excluded, archived through an ordinary path, or owned by another logical record. Grouped categories bind before their explicitly selected children. Excluded, mode-inactive and archived records retain those states; archive recovery uses its designated-location rules and cannot reactivate through this flow. Missing targets remain retained. No discovery of unrelated folders as a side effect.
4. A service-memory single-use token binds initiating workspace/current source ownership, evidence/policy version, complete old associations, fresh durable AND mount observations, mappings, mode/configuration, source evidence revision and all outstanding operation reservations. Apply accepts IDs/token, never client-supplied trusted evidence. Rescan and revalidate before/inside/after the transaction; stale or changed evidence rejects the whole application. A storage failure rolls back all metadata writes and emits no committed event. No filesystem effect occurs.
5. Commit only accepted evidence/mappings and one source evidence-generation change, plus discovery revision if the visible association projection changes. Preserve authored metadata and its independent revisions. Invalidate all affected sibling reviews/authorizations and publish committed source/project changes. Cancel, restart, workspace removal and backend replacement discard tokens; reconnect never replays Apply. Reopening verifies new evidence again.

Different enrolled volume evidence means **different volume**, not proven malicious replacement. Different sufficient folder evidence on that volume means **folder identity changed**. Neither automatically overwrites an enrolled binding. The first rollout allows explicit mapping of legacy-unverified records and scope-unverified records whose sufficient durable volume/folder evidence still matches; a lost/different installation anchor makes an enrolled record scope-unverified, not legacy. Those records use the same explicit mapping flow to enroll into the current installation, without overriding any durable mismatch. Re-enrollment invalidates prior operation authority: unfinished journals from another/lost installation scope remain uncertain and reserved, requiring a separately accepted recovery design rather than a new execution permit. Already-enrolled durable mismatch remains blocked, with retained data, connect-correct-volume/Refresh guidance and the existing separately reviewed project recovery where its contract permits. Whole-source replacement/relocation and overriding a durable mismatch need separate owner-approved scope. A missing or unsupported provider cannot complete even an explicitly requested legacy binding: preserve metadata, explain why folder access is blocked and allow retry with supported evidence. This conservative availability tradeoff requires owner acceptance.

## Rollout and boundary coverage

#71 must land a backend-enforced identity-policy capability gate **before** exposing newly bound sources to old consumers. Do not rely on disabled buttons. For a source using the new policy, deny all identity-sensitive mutation/recovery/native-dispatch entry points until their #72 capability is enabled. The gate covers fresh sources as well as migrated ones; retained logical metadata editing and saved views stay usable. Unknown policy versions fail closed. No legacy downgrade of a newly enrolled association is permitted.

| Boundary / current source map | #71 responsibility | #72 enablement requirement |
| --- | --- | --- |
| `discovery.ts`, `workspaces.ts` foreground preview/Apply and mode changes | Typed evidence, conservative legacy interpretation, source/category/project binding, source evidence generation | Any mode/Apply path that can bypass enrollment remains denied |
| `background-discovery.ts`, `discovery-worker.ts`, `source-observer.ts`, `external-reconciliation.ts` | Same versioned policy in workers and foreground; reservations loaded before scans; no automatic legacy adoption; discard old-generation worker results | Retain current policy on every watcher/restart route |
| `project-recovery.ts`, `category-options.ts`, `category-removal.ts` | Source-binding review only; block existing reassociation and category configuration/physical mutation consumers until converted | Fresh current root/parents/target, ownership, reviewed impact and reservations; no category/child adoption by side effect |
| `project-creation.ts`, `project-rename.ts`, `project-category-move.ts`, `project-archive.ts`, `project-archive-mutations.ts` | Gate commands, status-derived recovery actions and original-operation retries; expose retained statuses without replay | Shared new-policy authorization, versioned intent/evidence, no-overwrite, archive/restore parent/staging paths and crash recovery |
| `project-filesystem.ts`, `project-rename-filesystem.ts`, `project-reveal.ts`, trusted main/native Reveal | Deny dispatch/permits under new policy until converted | Revalidate current mount at the actual permit/effect boundary; never trust renderer evidence |
| `project-files.ts`, `project-file-target.ts` | Gate live file listing/Open/Reveal until targets/components use the new policy; metadata still readable | Convert any remaining file/native target path, invalidate stale target tokens |
| `project-rename-reservations.ts`, all creation/rename/category-move/category-removal/archive journals | Preserve legacy reservations and immutable receipts; load before discovery; expose unsupported recovery truthfully | Complete old/new journal handling below, including compound operations |
| `data-recovery.ts`, `data-recovery-invariants.ts`, DB schema/migrations, backups and startup | Validate old/new evidence versions and ownership without filesystem adoption; restore invalidates all runtime authority | Keep matching-version restore; no old binary consuming a new-schema database |
| `src/contracts/`, service entry, backend controller, preload/client and UI | Exact typed status/token validation, EN/RU reasons; generation invalidation reaches every transport route | No UI, sibling workspace, native permit or retry bypass of capability gate |

#72 enables capabilities per converted and verified boundary, not by the presence of a new root UUID. Until all affected paths are covered, the backend rejects the action with an explicit upgrade/recovery-required reason. Integration tests must directly invoke gated service/IPC/retry paths and prove no filesystem/native effect. Do not ship an intermediate combination that silently falls back to old consumers. Existing legacy-only sources remain retained/unverified under the same gate, not an unguarded exception.

### Review tokens and operation history

All discovery/mode, reassociation, category-removal, archive/restore, group-assignment and filesystem recovery reviews, project-file targets and native permits bind source evidence generation and current mount observations. Source rebind, policy change, remount, association/reservation change, service restart or stale worker generation invalidates relevant tokens. Property-only edits retain their existing independent revision semantics. A successful durable comparison is never itself an execution permit.

New journals bind evidence/policy version, immutable root/each parent/project/staging/destination evidence and original request. Preserve stable operation IDs, original request matching, no-replay semantics, reservations and commit-before-effect/evidence-before-completion stages. Status, startup, watcher events and transport reconnection never perform effects. Revalidate mounts immediately around each effect and completion; observed change retains uncertainty.

Legacy terminal receipts stay byte-for-byte immutable. Same-operation terminal retries return the stored result without reexecuting an effect, even if filesystem evidence is now unavailable. Legacy unfinished journals retain all reservations and cannot acquire new durable evidence through source rebinding alone. #72 may attach a separate, append-only reviewed attestation binding the operation, immutable legacy evidence, new source generation and fresh durable/current observations **only when every recorded legacy root/parent/object triple still matches exactly, including `dev`**, placement is unique and all existing recovery requirements hold. Never rewrite historical intent/evidence or change reserved IDs.

If recorded legacy evidence differs after a device-number change, the historical operation cannot be proven by the new source binding; recovery stays blocked/uncertain with reservations intact. Show the operation and manual-resolution/support guidance, never mark it failed/completed merely to unlock a path. A future reservation-release or mismatch override needs its own accepted design; it is not a hidden action in #71/#72. Legacy creation intent without recorded destination evidence keeps ADR 0006's explicit `associate_reviewed` option only after exact root/parent validation and fresh per-operation consent; a recorded conflicting destination never uses that exception. New-policy operations with sufficient immutable durable evidence may recover after a between-run remount through a new explicit review, while a remount during that review invalidates it.

## Truthful recovery states and journey

The following are semantic states; #71 defines exact wire names without conflating them with record association states. Retained projects, values, tabs and views remain visible; folder-backed actions explain their disabled state. Sources and project recovery link to the same source-level review and outstanding operations.

| Condition | User-facing meaning / proposed EN and RU wording | Available next step |
| --- | --- | --- |
| Missing/disconnected root | Source unavailable / Источник недоступен | Connect volume, check access, Refresh; never mass-mark projects deleted |
| Permission failure | Cannot inspect source / Не удалось проверить источник | Fix access, Retry; no replacement claim |
| Legacy without volume history | Folder association needs review / Требуется проверить связь с папкой | Review explicit mappings; keep retained metadata |
| Missing durable attributes/provider | Folder identity cannot be verified / Не удалось проверить идентичность папки | Explain unsupported/missing evidence, Retry; no blind adoption |
| Different durable volume | A different volume is connected / Подключён другой том | Connect expected volume, Refresh; legacy mapping only under its explicit flow |
| Different sufficient folder evidence | Folder identity has changed / Идентичность папки изменилась | Retain old record; eligible project recovery or separate source replacement decision |
| Duplicate/conflicting evidence, link or substitution | Folder association is ambiguous or unsafe / Связь с папкой неоднозначна или небезопасна | Resolve conflict, remove link from selected route, Refresh; no effect |
| Stale review or remount during operation | Folder state changed; review again / Состояние папки изменилось; проверьте ещё раз | Refresh and review; inspect uncertain operation if an effect was possible |
| Unfinished legacy journal not provable | Interrupted operation needs manual resolution / Прерванная операция требует ручного разрешения | Inspect retained operation/support guidance; no automatic replay or reservation release |
| Boundary still gated | Folder action awaits safety update / Действие с папкой ожидает обновления проверок безопасности | Read/edit retained metadata; retry after capability update |

## Primary-source basis and limits

These APIs support the proposed acquisition strategy; platform persistence, capability detection and packaging still need implementation evidence. They do not prove historical continuity for legacy data.

- [Apple filesystem attribute definitions](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/attr.h) define volume UUID/file-ID attributes and persistent-object capability. [Apple getattrlist documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/getattrlist.2.html) describes attribute support and volume-root query restrictions. The adapter must validate actual returned support.
- [Microsoft FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) provides a volume serial and 128-bit file ID. [Naming a Volume](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-volume) describes volume GUID paths and their non-unique aliases. Requiring both a volume binding and supplementary creation time is this proposal's conservative policy, not an OS guarantee against cloning/reuse.
