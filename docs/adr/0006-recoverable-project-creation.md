# ADR 0006: Recoverable project creation with a bounded filesystem adapter

## Scope and implementation status

This decision covers creation of one project directory in an applied direct source or an existing valid active grouped category. It extends [local folder identity](0004-local-folder-identity-without-markers.md) and the [local backend](0003-separate-local-backend.md). It does not introduce category creation, a general mutation framework, folder deletion, synchronization or release policy.

The foundation, creation, recovery and transport slices implement typed contracts, migration 0008, the source-owned operation journal, explicit recovery, discovery reservations and creation through the production service/client boundary using the bounded Node adapter. Trusted native Reveal is wired through the service/main boundary. EN/RU product UI, permanent Ladle fixtures and local development/packaged native scenarios are implemented. Actual results and pending coordinator platform acceptance are separated in [T10 verification](../verification/issue-17-create-reveal.md) and [the accepted plan](../plans/completed/issue-17-create-reveal.md).

## Durable intent and identity

The client supplies an operation UUID, initiating workspace UUID, authored basename, expected discovery revision and mode, plus a category UUID only in grouped mode. It supplies no destination path, native evidence or project UUID. Validation rejects altered/extra fields, unauthorized identities and unsafe platform names without trimming or renaming valid authored text.

Before mkdir, the service commits a source-owned project_creation_operations row containing a fresh reserved logical project UUID and immutable request binding: initiating workspace, source, name, mode, revision, category, canonical root, relative parent/destination, full root/parent identity, exclusions and archive designation. No project record or Text value exists for this UUID yet. The initiating workspace ID is historical context, deliberately without a workspace foreign key. Source/category ownership uses foreign keys; deleting a workspace cannot erase the operation. Reusing the source exposes its outstanding history through a referencing workspace, while the original command binding remains immutable. Sibling recovery must validate current same-source authorization; a retry of the original command must match its original binding exactly.

Migration 0008 requires current applied configuration and an active same-source category when inserting intent. It protects the immutable request, retained history, reserved UUID and full serialized evidence. A partial unique source/path index reserves outstanding destinations in intent, evidence_recorded and uncertain stages. Insert guards also reject replacing existing operation IDs, reserved project IDs or outstanding paths through [SQLite REPLACE](https://www.sqlite.org/lang_conflict.html), whose implicit deletion can bypass delete triggers. The service must additionally handle platform aliases, historical path/native reservations and observer/Apply/reassociation/reconciliation conflicts; exact SQLite text uniqueness is not filesystem case equivalence. Completed/failed rows retain the UUID and history, with existing project/history policy supplying completed reservations. Completed receipt locators/evidence are excluded from extra operation reservations: a verified move or explicit reassociation releases the vacated original path without altering the immutable receipt or its no-replay retry behavior. Unfinished reservations and actual historical project/category reservations remain protected.

## State machine and recovery

| Persisted stage | Meaning | Allowed next stage |
| --- | --- | --- |
| intent | Request committed; mkdir may or may not have happened; no destination evidence recorded | evidence_recorded, uncertain, failed |
| evidence_recorded | Sufficient destination evidence committed; metadata not completed | completed, uncertain |
| uncertain | Interrupted or changed outcome requiring explicit review; may retain immutable recorded evidence | evidence_recorded after explicit fresh validation/recovery |
| completed | Project association, source revision and completion committed together | Terminal |
| failed | Definitely no owned filesystem effect; useful failure recorded | Terminal |

The database guards stage/evidence consistency and transitions. Once destination evidence is recorded it cannot be replaced or cleared, even on uncertainty. Completion requires the reserved active project at its bound source/path/category/native identity and the committed source discovery revision. The service commits project metadata, completion and one discoveryRevision increment in one transaction and emits actual sibling events only after commit. It preserves workspace views, independent Text/category-label revisions and existing exact values; the new UUID inherits no values.

Same-operation command retries first reconcile the durable record. Completed retries return the stored result fields and completion revision without another mkdir or revision increment, even if the folder subsequently changes. Failed retries return the terminal failure. Changed payloads fail. Queries, startup and reconnection inspect state without replaying mutations. Outstanding reservations must be loaded before observation can enroll a destination under another ID.

Explicit status and recovery distinguish three reviewed actions:

- retry_missing permits exclusive mkdir at a freshly validated absent destination using the reserved UUID. Absence must be established under the unchanged valid source/parent; it is not permission to overwrite a replacement.
- complete_recorded completes metadata only for sufficient unchanged recorded evidence, with fresh source/parent/destination checks and conflict review.
- associate_reviewed is an explicit user acceptance of uncertain ownership for an existing freshly reviewed real folder when no sufficient destination evidence was recorded. A service-memory review token binds the observed folder, current revision, operation and workspace; revalidation is mandatory. Neither path nor emptiness proves ownership. A replaced folder with previously recorded evidence must remain unresolved, not acquire new evidence by this action.

Missing, replaced, linked, inaccessible or conflicting destinations remain visible cases when the selected action cannot safely proceed. Operation IDs and reserved UUIDs never change on recovery. A crash after mkdir but before evidence remains uncertain even if the directory is empty; an existing nonempty directory is likewise not adopted silently. While a transport outcome is uncertain, the UI retains the exact original request as well as its operation ID. Explicit Retry original request delivers a missing request or reconciles an accepted one using the same payload, including its original revision. Definite no-effect rejection restores editing; durable unresolved effects require reviewed recovery. Backend reconnect, list reload and cancellation never replay it automatically.

UI cancellation stops waiting/review only; it does not reverse an accepted filesystem effect.

## Crash windows

| Interruption point | Durable information | Required behavior |
| --- | --- | --- |
| Before intent commit | None | No mkdir; a fresh command can be submitted |
| After intent, before mkdir | Immutable request and reserved UUID | Visible outstanding operation; status cannot assume mkdir never happened |
| After mkdir, before evidence commit | Intent only | Ownership uncertain; preserve the folder and require explicit review |
| After evidence, before final metadata commit | Intent and full destination identity | Fresh unchanged evidence allows explicit completion |
| During metadata transaction | Evidence; all final writes commit or roll back together | Preserve one reserved ID and expose incomplete state if not committed |
| After commit, before response | Completed association and result revision | Same-operation retry returns the recorded result without repeating effects |

An exception is not a process-crash test. Crash fixtures terminate child processes abruptly at each boundary so cleanup cannot mask the persisted state. A failed attempt to record uncertainty must still leave a visible intent/evidence row from which status derives the unresolved outcome. Never recursively remove directories or remove a folder after third-party content appears. The supported recovery policy retains effects rather than promising filesystem rollback.

## Supported filesystem adapter and limitations

Use the existing Node filesystem APIs: lstat with bigint statistics, realpath and exclusive nonrecursive mkdir (recursive false). Full identity uses lossless dev, ino and positive birthtimeNs, not mutable timestamps. The adapter reuses existing containment/identity rules and introduces no native addon or new dependency.

Creation preserves the authored basename. Windows validation rejects reserved characters/device names (including superscript COM/LPT digits), trailing dots/spaces and oversized components according to the [Windows naming conventions](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file). POSIX colon, backslash, whitespace and line-break names are preserved; the mounted filesystem enforces its component-length limit. Malformed Unicode is rejected before Node can replace an unpaired surrogate. Hidden/service candidates, manual exclusions and designated archive containers are ineligible. Case/Unicode-equivalent existing entries and historical reservations are conservatively conflicting on every platform; this policy does not rename the request or infer ownership from an alias.

Validate the applied canonical root, directory kind, full identity and absence of links; validate the grouped category's same-source active/current-mode ownership, relative path, full identity and real directory kind. Check exclusions, archive containment, history and reservations before committing intent. Repeat canonical root/parent/link/full-identity checks immediately before and after mkdir, before recording destination evidence and around the final metadata writes/commit. Observed swaps prevent successful completion; effects already made remain recoverable. Use disposable roots, inventories and sentinels for race tests and separately account for external moves injected by a test.

These path-based calls do not provide atomic filesystem confinement. A concurrent ancestor move or replacement after validation and before mkdir can redirect an effect or leave the new folder outside the expected locator. Subsequent checks may detect the change but cannot guarantee rollback or locate every moved effect. Persist the available evidence and report uncertainty; do not claim a filesystem lock, atomic filesystem/SQLite transaction or guaranteed confinement against an adversarial concurrent writer. Native Reveal has a similar validation-to-path-invocation window; its trusted dispatch checks are described below.

Destination evidence is obtained by lstat after mkdir, rather than by an atomic handle-returning creation primitive. An unobserved destination substitution before that first observation is another remaining path-based race; repeated checks detect observed substitutions and do not constitute proof against every concurrent writer.

[Node 22.21.1 filesystem documentation](https://nodejs.org/download/release/v22.21.1/docs/api/fs.html) defines these APIs, bigint stat evidence and nonrecursive mkdir behavior. Their repeated use is the bounded supported adapter, not a native handle-relative confinement primitive.

## Trusted native Reveal

workspace.revealProject accepts exactly workspace and project UUIDs. The backend validates same-source ownership, the applied source mode/root evidence, active project/category state, current exclusions/archive policy, historical and outstanding reservations, and the selected directory's full native identity and canonical containment. Mode-inactive projects report mode_retained; missing, replaced, linked, excluded, ambiguous and unavailable folders do not dispatch. The read does not mutate project metadata or discovery/property/view revisions.

The service entry sends a private native request over the existing service/main port with the initiating request ID, a fresh dispatch UUID and trusted root/category/destination evidence. BackendController accepts it only for one currently pending Reveal request in its current backend generation. These messages never travel through renderer/preload notifications or results. No renderer path, URL, command or native evidence is accepted for Reveal.

Before dispatch, main requests backend reauthorization bound to the pending dispatch. The backend rereads ownership, configuration, associations, reservations and filesystem evidence; main repeats directory-kind, link, canonical-path, accessibility and full-identity checks. macOS invokes Electron shell.showItemInFolder synchronously after these checks, including real directory packages without desktop-default opening.

Windows uses fixed shipped PowerShell resources outside ASAR. It opens the authorized parent once, binds exactly one matching Explorer HWND/process/Document and captured full-path FolderItem, and waits for Busy=false/ReadyState=4 under one monotonic ten-second navigation/command budget. READY triggers a second backend reauthorization and synchronous main target/current checks and the sole GO write in the same continuation, without another await. The child rechecks its captured binding and deadline before one FolderView.SelectItem with SELECT | DESELECTOTHERS. There is no fallback, automatic retry, input manipulation or second selection. DONE means the command returned and the binding remained current; independent exact selected-item observation remains separate.

PowerShell is resolved from the main process's unique co-located loaded kernel32.dll and ntdll.dll System32 module paths, with canonical-path validation. It does not use PATH, SystemRoot, a fixed Windows installation drive or renderer-supplied executable/target data. Missing/ambiguous module evidence or unavailable resources returns native_unavailable. The transient process report is neither retained nor emitted. The owned application-script child uses -ExecutionPolicy Bypass only for its session, with no registry/persistent policy changes and no override of enforced MachinePolicy/UserPolicy. Policy/AppLocker/ConstrainedLanguage refusal fails closed without fallback. This trusts the running OS/module loader and installed application resources; it is not executable signature attestation. [Node's loaded-library implementation](https://github.com/nodejs/node/blob/v24.21.0/src/debug_utils.cc) uses EnumProcessModules/GetModuleFileNameW; [its report implementation](https://github.com/nodejs/node/blob/v24.21.0/src/node_report.cc) supplies sharedObjects. The actual Electron host shape remains a platform verification requirement.

The Windows bridge is bounded by twelve seconds from process launch plus one second for owned-process termination confirmation. The Windows native service wait is fifteen seconds and only its outer Reveal request is seventeen seconds; other requests retain their existing limits. Strict external selected-target observation and normal Electron quit each retain their ten-second deadlines. Abort signals, current-generation checks, protocol bounds and timeout stop only the owned PowerShell process, never shared Explorer. Shutdown awaits bounded native task cleanup. Before GO, cancellation prevents permission; after GO, dispatch may already be underway. Cross-process cancellation, backend policy and path mutation are not atomically locked. The child still revalidates binding/deadline, but an already started command cannot be undone. No automatic retry follows uncertainty.

Duplicate, foreign or malformed private messages and stale-generation replies cannot authorize another invocation. Paths/evidence remain private. A thrown error becomes a bounded native_error result without exception text. Successful adapters repeat filesystem checks and the backend repeats policy/evidence checks before responding. The public dispatched outcome acknowledges native command completion, not an observed Finder/Explorer selection. [Electron showItemInFolder](https://www.electronjs.org/docs/latest/api/shell#shellshowiteminfolderfullpath) returns void. Windows command receipt likewise does not replace exact observation or coordinator acceptance. Later detected changes may reject feedback but cannot undo native effects; no atomic filesystem confinement or native dispatch is claimed.

## Durability boundary

The current runtime sets SQLite WAL and foreign keys, and leaves synchronous/fullfsync settings at the driver's defaults. A committed operation is the recovery boundary for interruption of the service process. SQLite transaction recovery does not atomically synchronize directory creation with the database. No parent-directory fsync or filesystem durability protocol is introduced by this foundation.

SQLite documents that WAL with synchronous NORMAL can lose recent committed transactions on power loss, while FULL adds a commit synchronization; storage and OS behavior still matter. See [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) and [WAL durability](https://www.sqlite.org/wal.html). Until runtime settings and filesystem flush behavior are explicitly established and verified, this contract claims process-interruption recovery, not coordinated power-loss durability. A machine crash can leave a folder whose intent/evidence is missing; the application must not invent ownership or silently infer its reserved UUID.

## Verification

Foundation tests exercise actual populated migrations 0000–0007, migration 0008, reopen, immutable request/evidence, stage and destination reservations, source reuse after final workspace removal, ownership/category constraints and late migration-failure rollback. Creation tests add both modes, empty parents, exact requests, names/aliases, occupied entries, actual POSIX and simulated errno permissions, stale configuration/categories, historical/native reservations, multiple SQLite connections, source fanout/isolation and transaction/evidence failures. Real disposable root/category/ancestor link swaps and destination replacements preserve inventories/sentinels and explicitly demonstrate redirected effects during the residual mkdir race. Tests preserve existing IDs, selection/views, configuration, exact authored Text including empty strings, independent revisions and dormant history. Windows naming simulations are not Windows OS acceptance. Discovery/recovery and abrupt child-process crash tests establish process-interruption behavior. Reveal tests add real temporary service files/databases, private dispatch authorization, delayed folder/policy changes, malformed/foreign IDs, timeouts, stale generations and actual compiled entry/controller/preload/client routing. Native showItemInFolder functions in these automated boundary tests are injected: they do not establish actual Finder/Explorer opening or Windows acceptance. Permanent EN/RU actual React/real-service retry tests and both-mode vacated-path regressions cover the coordinator findings. Graphical/native local outcomes are recorded in the verification report; actual target-platform acceptance remains a coordinator gate. Native fixtures distinguish non-throwing shell.showItemInFolder invocation, localized dispatch feedback, exact disposable selected items, normal quit and restart. Historical openPath evidence retains its original milestone and cannot verify the repaired adapter. Historical fixtures used explicit Refresh synchronization and did not establish immediate-Reveal feedback. The continuation now exercises immediate creation-to-Reveal with production observation active; its local results and remaining coordinator gates are recorded in the verification report.

## File-manager-directed package handling

The review replaced desktop-default openPath with showItemInFolder because valid directory packages such as .app and .xcodeproj must be shown in the file manager rather than executed or opened in an editor. Package names remain valid. The graphical --directory-package fixture creates a wholly disposable harmless .app whose only possible effect is an owned launch marker, asserts that marker remains absent and records exact full-path Finder selection independently of native invocation. Actual repaired-adapter results belong to the review addendum in the verification report; target-OS acceptance remains separate.
