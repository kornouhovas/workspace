# Общие свойства и views через синхронизируемую папку

Исследовано 8 октября 2026 года. Статус: исследование и предложения для обсуждения, **не ADR и не реализованная возможность**. Действующие контракты Workspace остаются в силе.

## Продуктовая постановка

Режим по умолчанию остаётся локальным: приложение хранит данные на устройстве. Совместная папка подключается явно как дополнительный режим; серверный вариант рассматривается позже. В совместном режиме несколько компьютеров одновременно изменяют свойства проектов и общие views. Файлы проектов уже доступны через Google Drive либо сетевую папку. Пользователь хочет сохранить этот способ доставки файлов и использовать any-store для свойств и views.

Главное разделение: хранение актуального состояния на устройстве, доставка изменений между устройствами и правила их объединения — три самостоятельные обязанности. Выбор any-store решает первую, но сам по себе не решает остальные.

## Что подтверждено в Workspace и Any

- [go.mod](../../go.mod) закрепляет `github.com/anyproto/any-store v0.4.6`. [Store.Open](../../internal/workspacestore/store.go) вызывает `anystore.Open(ctx, path, nil)`; [sidecar](../../cmd/workspace-sidecar/main.go) по умолчанию открывает `workspace.db` и слушает loopback.
- README именно [v0.4.6](https://raw.githubusercontent.com/anyproto/any-store/v0.4.6/README.md) описывает документную БД поверх SQLite с транзакциями. В [драйвере этого тега](https://github.com/anyproto/any-store/blob/v0.4.6/internal/driver/manager.go) подключения открываются с `sqlite.OpenWAL`.
- [Главная ветка any-store](https://github.com/anyproto/any-store) уже описывает v2 с собственным движком. Это не версия данного проекта; её характеристики нельзя автоматически переносить на закреплённую зависимость. Обновление зависимости здесь не предлагается.
- Официальная [архитектура Any](https://docs.any.org/understanding/architecture.html) разделяет локальное хранилище `any-store`, протокол `any-sync` и обработку записей/CRDT в `any-sync-sdk`. У any-store самого по себе нет модели участников и синхронизации. `any-sync` передаёт подписанные зашифрованные изменения объектов, а SDK превращает изменения в локальные записи.
- В зависимостях Workspace any-sync отсутствует. Активный Electron пока использует JSON adapters для settings/views/properties; наличие Go-кода не означает его подключение. Это подтверждают [runtime guide](../development/architecture.md), [таблица областей данных](../data-model.md#current-runtime-and-target-scope) и [dispatcher](../../electron/workspaceIpc.js).

**Следствие для обсуждаемого продукта:** общие свойства и views могут храниться в локальном any-store каждого устройства, но для обмена нужны отдельные данные и правила. Синхронизация одного открытого файла БД внешним клиентом не подключает протокол Anytype.

SQLite отдельно предупреждает об ограничениях сетевых файловых систем; WAL требует, чтобы процессы, использующие одну БД, находились на одном хосте. Поэтому файл v0.4.6 нельзя считать готовой многопользовательской БД на сетевой папке. [SQLite over a network](https://www.sqlite.org/useovernet.html), [SQLite WAL](https://www.sqlite.org/wal.html).

## Прецеденты: файловый транспорт и слияние

| Система | Подтверждённый подход | Значение для Workspace |
| --- | --- | --- |
| Joplin | Локальное приложение синхронизирует отдельные items через `Synchronizer` и `FileApi`; драйверы поддерживают операции над файлами, включая локальную файловую систему. Состояние синхронизации сохраняется по item и target. | Можно отделить локальную БД от файлового формата обмена. Один transport adapter не заменяет synchronizer. |
| Syncthing | При конкурентном изменении файла сохраняет конфликтную копию; она распространяется как обычный файл. Использует временные файлы при получении, watcher и периодические полные сканирования. | Доставка байтов не знает, что одно изменение касается бюджета, а другое — ширины колонки. Conflict-copy нужно уметь распознать и обработать на уровне приложения. |
| Any | Синхронизируются изменения объектов, а не файл материализованной БД. Локальная БД обслуживает чтения и записи; фоновая синхронизация обменивается изменениями. | Это архитектурный прецедент разделения обязанностей; готовый адаптер Any для Google Drive им не доказан. |

Источники: [Joplin sync](https://joplinapp.org/help/dev/spec/sync/), [Syncthing synchronization](https://docs.syncthing.net/users/syncing.html), [Any local-first](https://docs.any.org/understanding/local-first.html).

Joplin сохраняет конфликтную версию для сравнения пользователем. Актуальная техническая документация также описывает трёхстороннее слияние `base/local/remote`: непересекающиеся изменения объединяются, неоднозначные остаются конфликтами. Если общей базы нет либо алгоритм превышает ограничения, используется fallback. Это прецедент осторожного слияния с сохранением альтернатив, а не универсальный алгоритм для структурированных views. [Пользовательские конфликты Joplin](https://joplinapp.org/help/apps/conflict/), [Joplin auto-merge](https://joplinapp.org/help/dev/spec/conflict_auto_merge/).

Документированный lock-протокол Joplin различает обычную синхронизацию и исключительную миграцию target, имеет обновление/истечение блокировки. Его нельзя переносить без доказательства свойств нового транспорта: наличие файла `lock` в одной локальной копии Drive не доказывает, что другая копия его уже видит. Последнее — вывод для предлагаемого протокола. [Joplin locks](https://joplinapp.org/help/dev/spec/sync_lock/).

## Что дают CRDT, и чего они не обещают

- **Automerge:** разные поля объединяются; при конкурентных значениях одного поля определяется одинаковый победитель, а альтернативы доступны через `getConflicts`. Порядок определяется идентификаторами операций, включая счётчик и actor ID, а не часами компьютера. Это обеспечивает одинаковое состояние, но не угадывает нужное пользователю значение. [Conflicts](https://automerge.org/docs/reference/documents/conflicts/).
- **Точность изменений:** замена целого вложенного объекта создаёт более грубый конфликт, чем изменение конкретного поля или элемента. Поэтому изменение цвета Select не должно переписывать весь каталог свойств, а изменение ширины колонки — весь view. [Automerge lists](https://automerge.org/docs/reference/documents/lists/).
- **Yjs:** обновления коммутативны, ассоциативны и идемпотентны; сходимость требует доставки всех изменений. Пользовательский транспорт всё равно нужно реализовать. Объединение бинарных updates само по себе не выполняет garbage collection. [Document updates](https://docs.yjs.dev/api/document-updates).
- **Хранение Automerge Repo:** уникальные incremental chunks и snapshots дают полезный прецедент сохранения изменений. Это не доказательство готовности произвольной синхронизируемой папки как адаптера и не готовая политика удаления файлов для Workspace. [Storage](https://automerge.org/docs/reference/under-the-hood/storage/).

Эти примеры обосновывают выбор готового проверенного механизма объединения вместо самодельного сравнения `updatedAt`. Конкретная библиотека, совместимость с Go и формат обмена пока не выбраны.

| Кандидат | Преимущество для обсуждаемого сценария | Обязательная дополнительная работа |
| --- | --- | --- |
| Ревизии сущностей и трёхстороннее слияние | Можно ограничить первоначальную модель известными полями, сравнивая общую базу и две версии. | Сохранять общую базу; определить поведение нескольких конкурентных ветвей, отсутствие базы и fallback с сохранением альтернатив. |
| Зрелый CRDT, например Automerge | Подходит для мелких offline-изменений нескольких участников; даёт определённые правила сходимости. | Проверить embedding, модель документов, adapter папки и материализацию в any-store. Готовность этой комбинации пока не доказана. |
| any-sync и соответствующий SDK | Отдельный стек обмена изменениями, с моделью spaces и участников. | Принять собственную сетевую синхронизацию метаданных; это другой способ доставки, чем Google Drive. |

Матрица — оценка применимости по источникам выше; она не выбирает библиотеку за пользователя и не требует от него выбора алгоритма до продуктовой семантики.

Для этого сценария первым кандидатом для узкой проверки предлагается Automerge: нужны независимые offline-правки нескольких устройств, изменения отдельных полей и доступ к конкурирующим значениям. Это рекомендация исследования, а не утверждение о готовой интеграции. Трёхстороннее слияние остаётся альтернативой для ограниченного набора типов; any-sync следует оценивать, если допускается собственный сетевой транспорт метаданных. Прототип в рамках исследования не создавался.

## Кандидат: локальный any-store и неизменяемые записи обмена

Далее — **предлагаемая архитектура для проверки**, не свойство перечисленных библиотек.

Предложение уточняет буквальную идею «перенести общую БД в папку»: в папке находился бы полный восстанавливаемый набор записей обмена/snapshots, а рабочая БД каждого устройства оставалась бы локальной. Этот набор должен позволять на чистом компьютере восстановить **и свойства, и общие views**, включая их определения и необходимые ссылки. Расположение рабочей БД вне общей папки пока предложено, а не принято: такое изменение способа хранения требует принятия как отдельного продуктового решения. Одни immutable-файлы не решают причинность и сходимость: это обязанность выбранного механизма объединения.

```text
Изменение свойства / общего view
  → локальная транзакция: change + outbox + проекция в any-store
  → файл с уникальным именем в каталоге обмена
  → Google Drive / сетевая папка доставляет файл
  → другой клиент проверяет и объединяет change
  → транзакция: inbox/dedup + проекция + история/конфликты
```

1. Каждое устройство держит свою рабочую БД **вне общей синхронизируемой папки**. В ней сохраняются и свойства, и views, а также долговременное состояние синхронизации.
2. Общий каталог содержит immutable change records или chunks проверенного CRDT. Записи создаются под уникальными именами; существующие записи не редактируются несколькими клиентами. Один общий дописываемый JSON-файл не используется.
3. Идентификаторы workspace/source/project/property/view стабильны и общие. Локальные абсолютные пути, настройки устройства и actor ID не принимаются за общую идентичность проекта или пользователя. Клон профиля не должен продолжать писать под тем же actor ID.
4. Пример полей envelope: `formatVersion`, `datasetId`, `changeId`, `actorId`, causal dependencies, checksum и payload. Конкретная CRDT-библиотека может уже определять часть формата; создавать второй несовместимый механизм причинности не нужно.
5. Локальная транзакция сохраняет изменение и outbox до публикации файла. Повторная публикация после сбоя безопасна благодаря тому же ID. Применение входящего изменения и отметка dedup сохраняются атомарно в локальной БД.
6. Импорт проверяет формат, dataset, целостность и зависимости. Неизвестные зависимости ожидаются; неподдерживаемая версия или повреждённая запись сохраняется для диагностики и не применяется как корректное изменение.
7. Повторная доставка, иной порядок файлов и конфликтная копия с тем же `changeId` не должны менять результат. Одинаковый ID с разным содержимым — ошибка целостности, а не правило «последний файл победил».
8. Локальная финализация файла выполняется через временный файл и rename, где это поддерживается. Протокол не переносит эту атомарность на несколько файлов или всю доставку Drive: получатель самостоятельно проверяет завершённость записи.
9. Watcher ускоряет обнаружение; периодическая полная сверка позволяет пережить пропущенное событие. Имя файла и `mtime` не являются единственным журналом применённых изменений.
10. Пользовательские действия проходят через один путь изменений. Материализованные свойства/views в any-store не становятся вторым независимо редактируемым источником истины рядом с CRDT/history.

Такой вариант совместим с намерением оставить файлы проектов во внешней папке. Он всё равно требует собственного слоя синхронизации метаданных: транспорт переносит файлы, а Workspace понимает изменения и конфликты.

Для первого режима принята граница доверия: участники с доступом к общей папке могут читать и изменять общие данные, включая views. Метка автора/устройства помогает разбирать историю, но не является криптографически подтверждённой личностью; checksum проверяет целостность, а не полномочия. Подписи и отдельные роли приложения для этого режима не требуются. Эту границу стоит пересматривать только при расширении требований к доступу.

## Предлагаемая семантика конфликтов

Ниже продуктовые предложения для согласования. Они не изменяют текущие Status/file-operation contracts.

| Одновременные действия | Предлагаемое поведение |
| --- | --- |
| Разные свойства проекта или разные настройки view | Объединять изменения по стабильным ID и конкретным полям. |
| Два значения одного Single Select, даты, бюджета или короткого текста | Детерминированно показывать одно значение; сохранять альтернативы, автора/устройство и контекст изменений. Неблокирующий индикатор позволяет выбрать нужное. |
| Ширина колонки, цвет, другие недорогие настройки вида | Автоматическая сходимость с историей; отдельный вопрос пользователю только при заметной потере намерения. |
| MultiSelect: добавить/убрать варианты | Операции над отдельными option ID; заранее определить add-versus-remove для конкурентного изменения одного варианта. Замена всего массива слишком груба. |
| Бюджет / числовое значение | Присваивание значения. Суммирование конкурентных значений допустимо только для явно выбранного счётчика, не для любого Number. |
| Порядок views, строк, колонок и вариантов | Отдельная модель последовательности и перемещения со стабильными ID. Нельзя обещать, что insert/delete автоматически сохраняет намерение конкурентных move. |
| Удаление объекта одновременно с редактированием | Явное логическое удаление и сохранение конкурирующей правки для восстановления; policy удаления должна быть определена. |
| Смена типа свойства, удаление используемого option | Проверка схемы и ссылок после объединения; несовместимые данные не превращать молча в пустые значения. |

Разрешение конфликта само публикуется как новое причинно связанное изменение. Общий модальный диалог, блокирующий весь workspace из-за одного значения, для этого кандидата не требуется. «Все реплики показывают одно» и «пользователь согласен с результатом» остаются разными критериями.

Показанный победитель не означает подтверждения спорного значения пользователем. Действия, для которых конкретное спорное поле определяет необратимый результат, требуют отдельного правила до выполнения; остальные части workspace остаются доступны. Общий список конфликтов должен быть доступен независимо от фильтров текущего view.

## Удаление, история и компактизация

Это требования к проектируемому протоколу, а не гарантии внешней папки:

- Удаление файла транспорта не означает удаление проекта/property/view. Предметное удаление представляется отдельным tombstone/change.
- Произвольная пропажа chunk — состояние неполной доставки или повреждения. Старый клиент не должен автоматически воскресить удалённый объект при появлении своей копии.
- В первом пилоте безопаснее сохранять журнал, измерять рост и не удалять старые изменения автоматически.
- Snapshot должен фиксировать, какие изменения и удаления он включает. Запись snapshot не доказывает, что другие устройства его получили.
- Удалять изменения после snapshot можно только по проверенному протоколу: определить множество реплик, подтверждения, судьбу долго отключённых/утраченных устройств и полное восстановление старого клиента.
- Срок хранения сам по себе не доказывает безопасность очистки: устройство может оставаться офлайн дольше. Альтернатива — ограничение поддерживаемого возраста реплики и обязательный bootstrap, явно видимые пользователю.
- История, необходимая пользователю для аудита/восстановления, имеет отдельный срок хранения. Внутренняя CRDT-компактизация не автоматически заменяет эту историю.

## Google Drive и сетевой каталог: подтверждённое и неизвестное

Google документирует streaming и mirroring: mirrored files доступны локально; streaming зависит от облачного содержимого и выбранной доступности offline. Для Workspace наличие имени файла в дереве поэтому не равно наличию его байтов offline. [Google: stream and mirror](https://support.google.com/drive/answer/13401938?hl=en).

Google также описывает уведомления об ошибках и возможность приостановить синхронизацию. Следовательно, успешная локальная публикация не является подтверждением доставки другим участникам. [Google Drive for desktop](https://support.google.com/drive/answer/10838124?hl=en).

В просмотренных официальных источниках не найдено достаточной гарантии для `.workspace`/других скрытых папок, порядка доставки, максимальной задержки и атомарной видимости нескольких файлов. Нельзя утверждать ни что скрытые папки всегда пропускаются, ни что всегда доставляются во всех режимах. Имена, разрешения, offline hydration и поведение при смене режима требуют пилота на поддерживаемых ОС/версиях. Syncthing отдельно резервирует собственные префиксы и имеет ignore rules; их нельзя переносить на Drive. [Syncthing ignores](https://docs.syncthing.net/users/ignoring.html), [Syncthing temp files](https://docs.syncthing.net/users/syncing.html#temporary-files).

Сетевая папка отличается от нескольких локальных копий Drive: клиенты могут видеть один серверный каталог. Однако гарантии блокировок, rename, reconnect и кеширования зависят от протокола/сервера. Для первого кандидата общий формат неизменяемых записей позволяет не делать общую живую SQLite-файловую БД обязательным условием.

Наличие записи на диске позволяет показать «сохранено локально»; публикация — «передано в папку обмена». Утверждение «получено всеми» требует собственного протокола подтверждений с известным составом устройств. При внешнем Drive-клиенте состояние его очереди не следует угадывать по локальному `write()`.

## Граница с физическими папками проектов

Объединение свойств не даёт транзакции для перемещения реальной папки. Сегодня Status-переносы физические и имеют собственный журнал восстановления: [Status move API](../api/workspace-status-move.md).

Для нового продукта нужно отдельно определить, исполняется ли перемещение один раз на общем файловом сервере либо на каждой локальной реплике. Повторить один путь на всех машинах опасно: файлы уже мог перенести Drive. Конкурентные rename/move/archive требуют сверки идентичности и текущего файлового состояния; их нельзя автоматически трактовать как независимые скалярные metadata edits.

## Проверка кандидата до принятия ADR

1. Три независимые локальные БД и изолированный каталог обмена: изменения разных полей/views, включая offline-ветви, сходятся без потерь.
2. Одно поле меняют offline одновременно: итог детерминирован, альтернативы доступны и разрешение повторно синхронизируется.
3. Дубликаты, перестановка доставки, пропущенная зависимость, обрезанный файл, конфликтная копия и неверная версия обрабатываются явно.
4. Падение после локального commit, после публикации и после импорта не теряет принятое изменение и не применяет его дважды.
5. Удаление-versus-edit, переименование Select-варианта, изменение типа свойства и конкурентный reorder сохраняют определённые инварианты схемы/ссылок/порядка. Поздно вернувшийся клиент, snapshot и bootstrap проверяются до очистки журнала.
6. Реальные Drive modes и SMB/NFS конфигурации проверяются раздельно; sandbox-испытание не объявляется поддержкой всех провайдеров.
7. Перемещения/переименования файлов тестируются отдельно; совпадение metadata replicas не является доказательством сохранности файлов.

**Открытые решения:** механизм слияния и его embedding, гранулярность CRDT-документа, смысл одинакового workspace на разных устройствах, политика удаления, список поддерживаемых транспортов и предел offline-периода перед bootstrap. Ни один из этих выборов не принят данным исследованием.
