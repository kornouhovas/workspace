# Проверки и доказательства

Проверки выбираются по затронутой границе согласно [AGENTS.md](../../AGENTS.md) и [quality gates](../workflow/quality-gates.md). Ниже краткий выбор; реальные npm-команды определены в [package.json](../../package.json).

| Изменение | Проверка |
| --- | --- |
| Только документация | Ссылки, согласованность, `git diff --check`; существующий docs check, если есть и затронут |
| Renderer | Релевантные Node tests, `npm run typecheck`, `npm run build:renderer` |
| Backend/domain/storage | Релевантные Node tests; при Go или sidecar-контрактах — `go test ./...`, `npm run build:sidecar` |
| Межслойное изменение, миграция, готовность к выпуску | Полный набор AGENTS.md один раз после интеграции: `npm test`, `npm run typecheck`, `npm run build:renderer`, `go test ./...`, `npm run build:sidecar`, `git diff --check` |

Для Node tests можно запускать выбранный существующий файл через `node --test test/<файл>.test.js`. В package.json также есть `npm run test:go` с `GOFLAGS=-buildvcs=false` и `npm run verify`, объединяющий программные проверки; diff проверяется отдельно. Отдельного docs check в scripts package.json сейчас нет. Для одних текстов сборки Electron/Go и программные тесты не требуются.

При UI-изменениях осмотрите затронутые поверхности Electron; для layout — 1440×960 и 1024×720. Отмечайте недоступную визуальную проверку. Успешная сборка не подтверждает поведение runtime или внешний вид.

## Запуск для проверки поведения

Из корня текущего checkout: `npm run dev` запускает Electron с Vite HMR и изолированными локальными метаданными/preferences. Для обычного запуска: `npm run build:renderer`, затем `npm run electron`; `npm run electron:build` объединяет эти действия. Компоненты доступны через `npm run storybook`; команды каталога описаны в [bb adaptation](../design/bb-stack-design.md).

Линтеры, каталог и `npm run test:desktop` запускайте по конкретному риску и требованиям затронутой задачи; они не добавляют обязательный полный прогон для каждой правки.

## Что считать доказательством

Баг локализуйте до исправления; для поведения и безопасности данных добавляйте регрессионные проверки наблюдаемого поведения. Разрушительные операции, recovery и миграции проверяйте только в изолированных временных fixtures, не на папках или метаданных пользователя. Приводите наблюдённый завершённый результат проверки, проверенный сценарий и ограничения. После успешных проверок повторяйте или расширяйте их при новых изменениях, сбоях или конкретном оставшемся риске.
