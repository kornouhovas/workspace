# Workspace

Workspace organizes real project folders through configurable views and properties. The current Electron desktop app supports settings, workspace management, reviewed direct/grouped discovery, external folder reconciliation, explicit folder recovery, recoverable project creation, native Reveal and shared Text properties, backed by a separate TypeScript service and SQLite.

**Current state:** a runnable local desktop app with English and Russian settings, workspace management and direct/grouped discovery. Users choose Root/Project or exactly Root/Category/Project for a new or configured source, edit manual exclusions and explicitly apply the reviewed project names to the default Table. Exclusions and opaque logical project IDs survive unchanged rescans and restart. Configurations over the same canonical root share applied projects and exclusions, retain distinct Table views and receive source-scoped notifications. Removal retains source/project metadata and external files, including after the last configuration is removed; a new configuration over that source reuses the saved projection. Unavailable sources retain their projection and expose a retry action. SQLite is device-local; discovery writes no marker files or project content.

Discovery excludes links/junctions, dot-prefixed folders, the Windows service directories $RECYCLE.BIN and System Volume Information (case-insensitive), and any persisted designated archive-containing child. An ordinary undesignated Archive folder remains eligible. Files are ignored and project contents are never scanned. Grouped mode treats every immediate root folder as a category, including direct-looking projects; only its immediate child folders become projects. Empty categories remain visible and persist after Apply. Apply rejects observed filesystem/configuration changes and requires another reviewed Apply. Discovery Apply reuses continuously matching same-path associations. Refresh source, bounded backend notifications and startup rescanning also recognize unique eligible moves of stored active folders under the same verified root; uncertain or persisted missing/unresolved records retain metadata for explicit recovery. Identity evidence and repeated validation are not a filesystem lock or a guarantee against indistinguishable native identifier reuse.

The default Table supports creating and renaming source-owned Text definitions and editing project values. Names and values preserve authored Unicode, whitespace and line breaks. An empty string is stored and shown as Empty text; Clear removes the value and shows No value. Sibling configurations share definitions/values while retaining independent view IDs; other sources remain isolated. Enter opens a cell, Enter in its textarea adds a line, Ctrl/Cmd+Enter saves and Escape cancels. Save, Clear and Cancel also have explicit buttons. Failed saves retain drafts, and same-field sibling changes show a notice without replacing unsaved text.

Text and required read-only folder-backed category values are implemented. Other ordinary property types, definition deletion/hiding/reordering, project rename/moves, filtering/grouping/dragging, Board/general view management, physical category editing, archive/restore, collaboration and AI remain future work. The previous implementation remains in Git history and on `codex/architecture-reference-docs`; importing its data is out of scope.

## Development

Use Node.js 22.12 or newer and npm. From a clean checkout, run `npm ci`, then `npm run dev` to build and launch the desktop app. The main checks are `npm test`, `npm run lint`, `npm run typecheck`, `npm run check:docs`, `npm run build`, `npm run build:ladle`, and `npm run smoke:runtime -- dev` for a real Electron launch. See [docs/development.md](docs/development.md) for artifact commands, data locations and implementation boundaries.

The standard application database lives at `userData/workspace.sqlite`; development uses `userData/development/workspace.sqlite`. Tests use temporary databases. Electron `utilityProcess` runs the local backend over message ports; it does not open a network listener. English is the default language, and the settings screen can save English or Russian for the next launch. A workspace stores a canonical folder association and its own active Table view; the Table shows applied project names, Text columns, required grouped category values and editable retained rows with distinct excluded, missing, unresolved, replaced and mode-change explanations.

## Change discovery mode

Choose Root/Project or Root/Category/Project in discovery review for an existing source. The preview identifies added projects, continuously retained associations, projects that will cease to be recognized, already-retained metadata, category-property availability and effective/inactive exclusions. Apply changes source configuration and associations atomically for every workspace over that source; Cancel saves nothing. Files and folder placement stay unchanged.

Projects paused by a mode change remain visible with their IDs, prior paths and editable exact Text values. Returning to the previous mode, Refresh, notifications and restart never silently reactivate them. Historical path/native reservations prevent duplicate enrollment; use explicit Locate folder and Reassociate at the current mode's depth. A folder changing between project and category roles receives a distinct role identity without inherited project values.

Direct mode hides categories and the category property while preserving their IDs, authored label and independent revision. A reviewed grouped Apply may resume dormant categories only when previously active/excluded associations still match the same path, native evidence and source root. Missing, unresolved, replaced or conflicting categories retain recovery restrictions; project recovery cannot repair them as a side effect. Text and hidden category-label drafts survive same-source mode changes.

Saved exclusions retain exact paths at either supported depth. A two-component exclusion becomes inactive in direct mode without expanding to its parent. A one-component exclusion applies literally: a project in direct mode or a category and its children in grouped mode. The preview explains that scope. Archive designation and containment remain unchanged; archive selection and folder commands are separate work.

Migration 0007 upgrades populated 0000–0006 databases without resetting metadata, settings, selection or independent workspace views. Mode and retained history persist after restart and final-workspace removal/source reuse. See [mode-change verification](docs/verification/issue-16-discovery-mode.md) for actual checks and outstanding platform gates.

## Locate a missing project folder

Retained projects keep their logical IDs and editable Text values. A complete scan can show an individual folder as missing, unresolved or replaced before discovery Apply. If the whole source is unavailable, unreadable or has conflicting root identity, Workspace shows source feedback once and retains the saved rows; it does not label all projects missing. Restore access to the original root and use Retry folder access. Moving a whole source to another root is outside this flow.

Choose Locate folder on a missing, unresolved, replaced or mode-retained row. Select a directory from the service-validated source-relative list, review the project, previous path, target path and category, then choose Reassociate. Selection and Cancel write nothing. Recovery does not require discovery Apply and changes only the database association: the same project ID and exact Text values survive restart. No project files are moved, created, renamed, merged or overwritten. Excluded rows use discovery exclusions for reinclusion; continuously valid active projects have no recovery action.

Direct targets must be Root/Project; grouped targets must be Root/Category/Project. Links/junctions, hidden/service folders, excluded paths and designated archive paths are unavailable. Another non-replaced record reserves its path, and conflicting current native identity evidence blocks selection. Historical replaced evidence alone does not establish live ownership. Grouped recovery reuses a continuously verified active category or atomically creates a genuinely new category. An existing missing, unresolved, excluded or conflicting category cannot be repaired through project recovery; choose another eligible category.

A changed review returns stale_preview: use Refresh, select the target again and explicitly confirm. If the service connection is lost after submission, the outcome is uncertain; Workspace reloads committed state without replaying the command or claiming success. Text and category-label drafts survive same-source refresh and recovery. Filesystem observations provide no lock: later changes and indistinguishable native identity reuse remain possible. Mode-retained projects require explicit target-depth recovery even after returning to their previous mode.

See [folder recovery verification](docs/verification/issue-14-folder-recovery.md) for local evidence and remaining platform gates.

## External folder changes

Use Refresh source to check external renames or moves without applying new discovery choices. Backend notifications and startup rescanning use the same validated reconciliation. A uniquely matched active project or category retains its logical ID, exact Text, category-property label and independent workspace views. Same-source Text and category-label drafts survive locator changes. When automatic updates are degraded, localized guidance keeps Refresh available.

Grouped moves reuse verified tracked categories. A known active project may also move into a genuinely new eligible category: only that needed category record is created, atomically with the placement. Unrelated children, other new categories and empty new categories remain choices for explicit Preview/Apply. Existing unavailable, unresolved, excluded, replaced or conflicting category associations require recovery; matching child evidence cannot repair them. The previous category stays retained when empty.

Matching requires unique unchanged lossless dev/ino/positive birthtime evidence and repeated complete scans. Paths, copied folders, case spelling and reused native IDs alone never establish identity. Case-only changes preserve exact directory spelling when evidence is sufficient; cross-volume, ambiguous or substituted evidence retains metadata. This cannot detect reuse of the entire evidence tuple and provides no filesystem lock. No marker or application-driven folder move is introduced.

Notifications watch only referenced source roots and, on macOS, eligible immediate category directories. Windows watches roots and checks grouped sources every five seconds without holding category watch handles; project contents, links and excluded targets are never traversed. Missed notifications, unavailable roots and degraded watchers can require explicit Refresh; startup scans recover changes made while stopped. Whole-root relocation and cross-computer identity are separate work. See [matching and observer details](docs/architecture.md#implemented-external-reconciliation-and-observation) and [actual local evidence and open platform gates](docs/verification/issue-15-external-reconciliation.md).

## Create a project and reveal its folder

Apply discovery configuration first, then choose Create project and enter a folder name. Direct mode creates Root/Project; grouped mode requires a selected existing active category and creates Root/Category/Project. Workspace never creates a category implicitly. Valid authored spelling is preserved; invalid platform names, occupied or reserved destinations, unavailable roots and stale categories produce localized feedback. A successful project receives a fresh durable logical ID and no inherited Text values; sibling workspaces share the result and retain independent views.

Creation commits durable intent before exclusive mkdir, records native folder evidence, then commits project metadata and completion together. Interrupted operations remain visible after restart and source reuse. Check operation status or review recovery explicitly. Recovery can retry a missing destination, complete metadata for unchanged recorded evidence or ask you to accept uncertain ownership of a reviewed existing folder. Existing paths and empty folders alone never prove ownership. A replaced folder with recorded evidence cannot be silently adopted. Cancel dismisses the form/review without undoing accepted effects.

If a response is lost, Retry original request explicitly sends the same operation ID and immutable payload. Reconnection, reload and cancellation never replay it automatically. A completed retry returns its original receipt without another folder or revision change, even after the project moves. The receipt does not permanently reserve its vacated old path; actual project/history and unfinished-operation reservations still apply.

Reveal starts from the selected logical project, validates its real folder in the backend and dispatches Electron's native openPath integration. EN/RU feedback distinguishes missing, replaced, unavailable and mode-retained folders. A dispatched message acknowledges the native API; observing a Finder/Explorer window is separate verification. Directory-package behavior (such as macOS .app folders) remains an open native acceptance concern because openPath uses desktop-default opening. Repeated path/native-identity checks cannot lock the filesystem: concurrent ancestor moves or destination replacement can redirect mkdir or native invocation between checks. There is no guaranteed rollback or coordinated power-loss durability. See [ADR 0006](docs/adr/0006-recoverable-project-creation.md) and [T10 verification](docs/verification/issue-17-create-reveal.md) for evidence and outstanding target-platform gates. Version remains 0.1.0; issue #44 remains open.
